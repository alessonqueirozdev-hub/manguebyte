# JUCE parity

Manguebyte's baseline goal is to offer everything JUCE offers. This page
tracks that goal module by module, against the 24 modules in JUCE's `master`
branch (version 9.0.4 when this was written, October 2026).

The module list is taken from the JUCE repository and its documentation
index. The feature summaries are a working description based on JUCE's public
documentation and will be refined into per-feature checklists as each area is
built. JUCE is a reference for scope here, never a source of code: see
[ADR 0004](adr/0004-juce-as-reference.md).

Parity means the same capability, not the same classes. Where Rust or its
ecosystem already solves something well, the plan says so instead of
rebuilding it.

Legend: ✅ done · 🚧 partly there · ⬜ not started · ➖ not planned as part of
Manguebyte

## Audio

| JUCE module | What it covers | Manguebyte | Status |
|---|---|---|---|
| `juce_audio_basics` | Audio buffers, sample conversion, MIDI messages and buffers, MIDI files, MPE, UMP, synthesiser voices, smoothed values, basic sources, ADSR | `core`, `midi`, `dsp`, `sampler` | ✅ Buffers, vector operations on them (`FloatVectorOperations`: `core`'s `vector`), smoothing, channel and system messages, SysEx, stream parsing, MIDI files, sample-accurate MIDI buffer and ADSR are done. Voice allocation is done too, with per-note expression. MIDI 2.0 packets (UMP) with MIDI 1.0 translation, RPN/NRPN, MPE zones and tracking, and keyboard state are done. A sampler is done too, as an SFZ player (`sampler`), with samples from files or from memory. MPE and MIDI 2.0 reach processors as per-note events (`dsp::note_input`), read once for devices, the standalone runner, the harness and every plugin wrapper, and audio sources are done: memory, a mixer, a sample rate converter, a channel router, a source through a processor and a source as a processor (`core::source`, `dsp::sources`). Processors write MIDI back out too: notes, expressions and any MIDI 2.0 channel voice message, as MIDI 2.0 packets, as MIDI 1.0 by the default translation, or as MPE (`plugin::output`, `midi::translate::Midi2ToMpe`), read back by the same `NoteInput`; a device port that speaks MIDI 2.0 receives the packets unchanged (macOS, iOS and Linux; `devices::midi::MidiOutput::open_with_protocol`). The play head is done: `AudioPlayHead`'s position (tempo, time signature, PPQ position, last bar start, bar count, time in samples and seconds, loop points, playing, recording, looping) is `dsp::Transport`, filled by every wrapper from what its format gives, and beyond what JUCE's modules offer, `dsp::timeline` has a tempo map with steps, linear ramps and time signatures, with exact conversions between frames, seconds, quarter notes and bars, beats and ticks, and a real-time transport clock an application owns (play, stop, seek, loop, a new map from another thread), which the harness and the standalone runner use. Left: per-note controllers with no expression to become ([TECH_DEBT](TECH_DEBT.md) item 76), what item 82 lists of the way out, and the play head's frame rate, host time and continuous time (item 86) |
| `juce_audio_devices` | Device enumeration and selection, input and output streams, per-platform backends (CoreAudio, WASAPI, ASIO, ALSA, JACK, Oboe, and others), MIDI ports, device manager with saved setup | `devices` | 🚧 Listing, selection by stable id, sample rate and buffer size, output, input, duplex and MIDI ports are done, and so are host selection (WASAPI, CoreAudio, ALSA and AAudio; JACK behind a feature; ASIO in the opt-in GPLv3 crate `manguebyte-pro-io`, which speaks to the drivers itself and runs behind the device manager through its backend seam, with driver resets followed by a restart, tried on three drivers (a Behringer UMC404HD's, FlexASIO, ASIO4ALL), or, for closed source, when the application turns on `cpal`'s own feature with Steinberg's SDK), hot-plug notification (by polling, as no backend notifies) with streams whose device went away reported lost, a device manager whose setup is saved as text and restored with fallbacks, virtual MIDI ports (macOS, iOS, Linux), system exclusive input for MIDI-CI (`MidiInput::open_with_sysex`), MIDI read into per-note events (`read_events`), audio sources played in a device callback (`dsp::sources::SourceProcessor`), timing in callbacks, duplex clock-drift correction by resampling, devices changed under a running engine without stopping or preparing it again (`DeviceManager::start_engine`: a crossfade where two streams can run at once, a short faded gap where they cannot, a resampler for a device at another rate; [BEYOND_JUCE](BEYOND_JUCE.md) section 17, [TECH_DEBT](TECH_DEBT.md) item 85), and a headless backend that tests all of it without hardware. Android and iOS are built in CI, not run. MIDI output from the audio thread, each packet sent when its frame is heard (`midi_output_queue`, `MidiOutput::spawn`): to a port that speaks MIDI 2.0, opened with `MidiOutput::open_with_protocol`, unchanged through the system's own Universal MIDI Packet output (CoreMIDI's `MIDISendEventList` on macOS and iOS, the ALSA sequencer's UMP events on Linux; `manguebyte-ump-io`), and as MIDI 1.0 bytes with the default translation to every other port, with the protocol of each port listed and the reason for MIDI 1.0 given. Missing: UMP output on Windows (Windows MIDI Services' API is not reachable from the `windows` crate; [TECH_DEBT](TECH_DEBT.md) item 90), UMP output tried with a MIDI 2.0 device (CI loops back to its own endpoints), UMP input, Oboe's other backends, the systems' own change notifications, a MIDI port's identity in the merged input, JACK tried on real hardware, ASIO under MIT (the SDK's own licence forbids re-working its interface inside a framework, see `manguebyte-pro-io`), ASIO clock sources and control panels in the device manager, a crossfade between two real outputs (the hot swap's crossfade is proven on the headless backend only) |
| `juce_audio_formats` | Readers and writers for WAV, AIFF, FLAC, Ogg Vorbis, MP3 and platform codecs; streaming sources; thumbnails cache; sampler | `formats` | 🚧 WAV (with RF64) and AIFF read and write, FLAC, Ogg Vorbis and MP3 (MPEG-1 layer III) decoding and encoding, Ogg Opus decoding and encoding (CELT frames: music; constant and variable bitrate, up to 255 channels), MPEG audio layers I, II and III of MPEG-1, 2 and 2.5 decoding, written from their specifications, gapless, format detection, streaming readers and writers with exact seeking, and wait-free play and record bridges for audio callbacks. Metadata in one model for every format: `LIST/INFO`, Broadcast Wave `bext`, `iXML`, cue points with labels, `smpl` and `inst` loops and root keys in WAV; `MARK`, `INST` and text chunks in AIFF, read and written; FLAC Vorbis comments and pictures, read and written; Ogg Vorbis and Ogg Opus comments and pictures, read and written; ID3v1 and ID3v2.2 to 2.4 read, ID3v2.4 written; every chunk not understood kept for the round trip. Waveform thumbnails (min, max and RMS at every zoom, built while a file streams in, on a thread of their own if wanted) with a compact cache file. AAC, ALAC and WMA through the system's codecs (Media Foundation on Windows, AudioToolbox on macOS) behind the `platform-codecs` feature. The SFZ sampler is a crate of its own (`sampler`), reading loop points and root keys from WAV `smpl` chunks. A transport source over a streamed file (`TransportSource`: play, pause, stop, seek and loop from any thread, sample-exact). Missing: Opus encoding of speech (SILK and hybrid frames), metadata of the formats the system decodes, a codec layer on Linux (see [TECH_DEBT](TECH_DEBT.md) items 75, 77 and 89) |
| `juce_audio_processors` | The plugin and processor model, parameters and their state tree, plugin hosting for VST3, AU, LV2 and others, processor graph, plugin scanning | `params`, later `plugin`, `host`, `graph` | 🚧 Parameters, state and the plugin model are done, with a different design ([ADR 0003](adr/0003-parameters-without-listeners.md), [ADR 0005](adr/0005-one-timestamped-event-stream.md)). The processing graph is done (`graph`), rewired while it plays: every node has a main input and a sidechain, connections name the bus and the channels, notes, parameter changes and MIDI travel along event connections on their frames (a node, such as a hosted plugin, can send them), feedback goes through a delay in frames so a loop sounds the same at any block size, and latency is compensated across audio, sidechain and event paths; crossfaded swaps and buffer reuse are still to come ([TECH_DEBT](TECH_DEBT.md) items 19, 20 and 88). Hosting CLAP, VST 3, LV2 and Audio Unit (version 2) plugins is done (`host`), through one interface for all four, with every event on its frame; LV2 bundles are read with the crate's own Turtle reader, and the example plugins hosted as LV2 sound the same, bit for bit, as with no host. Audio Units are found with `AudioComponentFindNext` and made through AudioToolbox on macOS, or in process from a factory function on any system, with stream formats, slices, channels, render callbacks for the input and sidechain, `AudioUnitScheduleParameters`, `MusicDeviceMIDIEvent`, the host's transport callbacks, latency, tail, `ClassInfo` state and bypass; the example plugins hosted through their factories sound the same, bit for bit, as with no host, and so do the installed units found through the system's registry and made through AudioToolbox, in the macOS CI job ([TECH_DEBT](TECH_DEBT.md) item 93). Plugin scanning is done: CLAP and VST 3 files and the units of AU bundles are listed in a process of their own with a time limit, so a plugin that crashes or hangs is reported and the host goes on, LV2 bundles from their Turtle files, with a cache keyed by path, time and size; not yet run against plugins from other vendors. The editors of hosted CLAP and VST 3 plugins open in a window the application owns, tested in real Win32 windows with an edit reaching the processor (issue #5, [TECH_DEBT](TECH_DEBT.md) item 95). The notes and MIDI a hosted plugin sends are read in all four formats, through one `AnyProcessor::output_events` (MIDI 1.0 from LV2 and AU, [TECH_DEBT](TECH_DEBT.md) item 82). Missing: hosted editors on macOS and Linux and for LV2 and AU, MIDI 2.0 out of hosted LV2 and AU plugins, Audio Units version 3 as such |
| `juce_audio_processors_headless` | The same, without GUI dependencies (added in JUCE 8.0.11) | the same crates | ✅ by construction: no processing crate depends on a GUI |
| `juce_audio_plugin_client` | Wrappers that turn a processor into a VST3, AU, AUv3, LV2, AAX, Unity or standalone plugin | `clap`, `vst3`, `lv2`, `standalone`, later one crate per format | 🚧 CLAP and VST 3 are done and pass their projects' validators in CI, and so is the standalone wrapper. LV2 is built and tested in process through its C interface, acting as a host, and `cargo mangue` bundles it; CI loads the example plugins' bundles with lilv, but `lv2lint` has not checked them and no LV2 host but the framework's own (`host`) has run one; it offers no editor. CLAP and VST 3 implement their editor interfaces (CLAP `gui`, VST 3 `IPlugView` and the component handler), and `gui` opens editors in a child window on Win32, tested headless through both formats' real interfaces and embedded in a real window. Both example plugins have an editor, and a test opens the two plugin binaries' editors in one process. By hand, Mangue Pluck's CLAP editor has been opened in REAPER on Windows, where it showed its title and knobs; working its knobs there, the VST 3 editors and Mangue Duck's editor are not tried yet. AU (version 2) is built by `au`: the plain C AudioUnit interface, declared from Apple's headers, with properties, parameters, sample-accurate scheduled parameters and MIDI, transport from the host's callbacks, state as `ClassInfo`; tested on every system through its C interface against a stand-in for CoreFoundation, bundled and installed by `cargo mangue`, and checked by `auval` in a macOS CI job, which both example units pass; no editor, no AUv3. A plugin that sends notes gets a CLAP output note port (CLAP notes and note expressions, `CLAP_EVENT_MIDI2` or `CLAP_EVENT_MIDI`, as the host takes them), a VST 3 output event bus (notes, polyphonic pressure, note expression values and legacy controller events) and the standalone runner's MIDI output port, an AU MIDI output (`kAudioUnitProperty_MIDIOutputCallback`, MIDI 1.0) and, in LV2, MIDI 1.0 on the notify port. CLAP also offers per-note automation and modulation, `voice-info`, `note-name`, `audio-ports-config` and `audio-ports-activation`, 64-bit ports and transport events inside a block; VST 3 takes `kSample64` and the bus arrangements of the layouts a plugin offers (`Plugin::LAYOUTS`), and AU the same layouts as its elements' channel counts. 64-bit audio goes through the plugin's 32-bit path everywhere; there are no program lists, presets or note-end events yet. JUCE has no native CLAP |
| `juce_audio_utils` | Ready-made audio widgets and helpers: device selector, keyboard, thumbnail, transport-style player | `ui` | 🚧 A waveform view (`AudioThumbnail` with `AudioThumbnailCache`'s role): a sample's channels drawn from a summary at several resolutions, exact against reading every sample, so a ten-minute file draws as fast as a short one; zoom around the pointer, scrolling, markers dragged within rules and onto zero crossings, a selection and a playhead. A piano keyboard (`MidiKeyboardComponent` with a `MidiKeyboardState`'s role): notes from the pointer with velocity from where a key is pressed, glissando, the computer's letters, keys the application lights, key ranges marked, polled as note events; each key named for assistive technology. Beyond the module: an ADSR editor bound to parameters through gestures, and a zone map of keys by velocities lined up with the keyboard. Missing: the device selector (`AudioDeviceSelectorComponent`), a transport-style player, thumbnails from a stream or a cache file, a spectrum view and an EQ editor ([TECH_DEBT](TECH_DEBT.md) item 98) |
| `juce_dsp` | FFT, windows, IIR and FIR filters with design methods, state-variable and ladder filters, oversampling, convolution, delay lines, dynamics, reverb, chorus, phaser, waveshaping, oscillator, panner, SIMD wrappers, lookup tables | `dsp` | 🚧 Processor chains, oscillator, biquad designs, state-variable filter, delay, gain, compressor, noise gate, reverb, FFT of any length and windows are done. Oversampling, resampling, look-ahead limiter, waveshaper, noise, LFO and FIR design are done as well, and so are the one-pole and ladder filters (the ladder's cutoff stops at 0.45 of the sample rate), high-order IIR design (Butterworth, Chebyshev I and II, elliptic, orders 1 to 16), Linkwitz-Riley crossovers, chorus, flanger, phaser, dry/wet mixing, panner, envelope follower and interpolated delay lines. Convolution (uniformly partitioned, with zero latency or a latency of one partition, true stereo, responses swapped while playing), a FIR filter processor, an expander, sidechain keying for the dynamics and a band-limited wavetable oscillator are done too, and so are spectral processing by short-time Fourier transform and weighted overlap-add (exact reconstruction, windows checked for constant overlap-add, a reported latency, output independent of the host's blocks) with a spectral gate and denoiser, a freeze and a basic phase-vocoder pitch shifter on it, and curves for drawing, computed from what the processors run on: the frequency response of every filter and of chains of them, the transfer curves of the dynamics and the shaper, envelope and modulation shapes, echoes and the reverb's decay. Vector operations on buffers, JUCE's `FloatVectorOperations`, are done in `core` (`vector`: gain, mixing, ramps, peak, sums, dot products, complex products, interleaving, integer conversions, on SSE2, AVX, AVX2, NEON and WebAssembly SIMD), and the convolution runs on them. Missing: a SIMD register type (`SIMDRegister`) for processors to vectorise themselves, SIMD in the FFT, filters and oversampler, lookup tables |
| `juce_midi_ci` | MIDI Capability Inquiry: discovery, profiles, property exchange | `midi::ci` | 🚧 Every MIDI-CI 1.2 message read and written (discovery, endpoint information, MUIDs, ACK and NAK, profiles, property exchange with chunking and Mcoded7, process inquiry, and the deprecated protocol negotiation), tested with hostile input, and an agent, responder and initiator in one with no I/O, that answers discovery and profile requests, chunks and reassembles properties, times requests out and moves its MUID on a collision. Missing: the property exchange resources themselves (JSON is carried, not parsed), profile details, a check against another implementation |
| `juce_osc` | Open Sound Control messages over UDP | `osc` | ✅ Messages, bundles, address patterns, UDP and TCP (OSC 1.1 framing), and a real-time bridge whose time-tagged bundles land on their frame. Missing: the OSC 1.0 TCP framing |

## Foundation

A large part of JUCE is a general-purpose C++ toolkit that predates the
modern standard library. Rust's standard library and ecosystem cover most of
it, so the plan here is mostly to not rebuild it.

| JUCE module | What it covers | Manguebyte | Status |
|---|---|---|---|
| `juce_core` | Strings, containers, files, streams, threads, time, XML, JSON, networking, memory utilities, logging | Rust `std` and established crates | ➖ except audio-specific pieces: lock-free queue ✅, atomic floats ✅, denormal guard ✅ (applied automatically, ADR 0006), logging that is safe on the audio thread ✅, high-resolution timer ⬜ |
| `juce_events` | Message loop, timers, async updaters, change broadcasters, inter-process connections | later `gui` for the event loop | ➖ as a general facility. The audio side deliberately has no broadcaster ([ADR 0002](adr/0002-real-time-thread-model.md)) |
| `juce_data_structures` | Value trees, undo manager, properties files | `state` | ✅ with a different design ([ADR 0008](adr/0008-application-state.md)). A document tree of typed properties (numbers, text, switches, bytes, references to parameters and to nodes) and ordered children, with ids that never change and are never reused. Every change is a named transaction that can be undone and redone; a gesture is one step, series of edits merge by key, a new step discards the redo branch, and history is bounded by steps and bytes. No listeners: readers drain a change journal with their own cursor, or poll a version from any thread. Parameters are mirrored on a node: a user's change is an undoable step, host automation is copied in by polling and never enters the history. The document is saved with a plugin's state (`ExtraState`, plugin state version 2), in a versioned text form or a compact binary one, both loaded tolerantly, with migrations for an application's older schemas. Settings files in the user's configuration folder (`Settings`). Snapshots of a document reach the audio thread without allocating (`state::snapshot`). Missing: timed coalescing, a value bound to one property (`juce::Value`), settings shared between processes; see [TECH_DEBT](TECH_DEBT.md) item 87 |
| `juce_cryptography` | Hashes, RSA, Blowfish | ➖ | Use RustCrypto |
| `juce_javascript` | Embedded JavaScript engine | ➖ | Use a dedicated crate |
| `juce_box2d` | Bundled 2D physics | ➖ | Use a dedicated crate |
| `juce_analytics` | Analytics event collection | ➖ | Out of scope |
| `juce_product_unlocking` | Licence key and online unlock helpers | ➖ for now | Revisit with the plugin tooling |

## Beyond parity

Things JUCE does not offer, or offers only in part, that Manguebyte commits
to. Each one is tied to something observable.
[BEYOND_JUCE.md](BEYOND_JUCE.md) explains the main ones in detail: the
problem, what JUCE does, what Manguebyte does, the test that proves it and
the limits of the claim.

| Area | JUCE today | Manguebyte |
|---|---|---|
| Real-time safety | A convention; the framework's own parameter attachments post to the OS message queue from the audio thread | Enforced: an allocation in `process` fails CI ✅ |
| Parameter threading | Listeners run on whichever thread changes the value, including the audio thread | No listeners; atomics and polling ✅ |
| State and processing | Host may call state functions concurrently with processing; each plugin synchronises | Parameter state is safe from any thread with no lock ✅ |
| Old sessions after a range change | Position-based automation and state can shift meaning | State stores real values by id; loading is tolerant and reports ✅ |
| Headless use | Split out in 8.0.11, still needs the event module | No GUI or event loop below the GUI crate ✅ |
| CLAP | Not available natively; promised for JUCE 9, not in 9.0.x | Native. Both example plugins pass every applicable test of `clap-validator` in CI (the instrument 35 of 44, the effect 33 of 44, none failed) ✅ |
| Sample-accurate automation | Not in `AudioProcessor` | Timestamped events in the process call, applied on their exact frame ✅ |
| Note expression, per-voice and non-destructive modulation | Not in the processor model | Part of the event model; the synth routes each to the right voice, and MPE and MIDI 2.0 are read into it and written back out of it, as MIDI 2.0, MIDI 1.0 or MPE and as CLAP and VST 3 note expressions ✅ |
| Arbitrary FFT length | Powers of two | Any length ✅ |
| Compile-time chains | Template chains exist; graph is dynamic | Tuples of processors inline end to end ✅ |
| Block-size independence | Left to each plugin; splitting a block is manual | Tested: a song rendered with six block patterns must match bit for bit ✅ |
| Testing a plugin | Needs a host, or a hand-built test rig | `Harness` schedules notes and automation and renders in a unit test, on CI machines with no sound card ✅ |
| Tempo map and transport | A play head reports what a host says; an application keeps its own time | A tempo map with ramps and time signatures and a real-time clock that plays it; the harness drives a plugin through tempo changes, and positions match bit for bit across block patterns ✅ |
| Changes from a UI or a state restore | Visible only to code that polls or listens | Turned into events on frame 0, so the event stream is a complete record of every change ✅ |
| Licence | AGPLv3 or commercial | MIT or Apache-2.0 ✅ |
